## Overview

Partner applications call Duluin's APIs on behalf of client companies. This work covers how those partners get access, how admin accounts are protected, and how authentication endpoints are protected from abuse.

## My contribution

- Contributed, as part of the team, to the design of the auth service and its OAuth2 client-credentials flow for third-party apps.
- Built client and tenant credential management in the admin dashboard, including approval-based key rotation.
- Added TOTP two-factor authentication to the admin dashboard.
- Built rate limiting in the API gateway and the auth service, plus admin tooling for inspecting and resetting limits.
- Worked with the team on the transaction PIN.

## Skills applied

- **OAuth2.** Client-credentials and refresh-token grants, scopes, and revocation.
- **Credential lifecycle.** Secrets stored as hashes, keys masked by default, rotation approved by a second person, and revocation that takes effect everywhere at once.
- **Two-factor authentication.** TOTP with recovery codes, encrypted secrets, and a lockout after repeated failures.
- **Rate limiting.** A token bucket per client in the gateway, shared across instances through Redis, and stricter limits on sensitive auth endpoints. Limits are keyed so that users who share an office IP aren't blocked because of one person.
- **Operational tooling.** Admins can inspect and reset limits without a deploy.

## Outcome

- Partner apps integrate through scoped, rotatable credentials; the [cross-app claim integration](/projects/claim-integration) runs on them.
- Operations can create, rotate and deactivate partner credentials from the dashboard without engineering help.
- Admin accounts are protected by a second factor.
- Abusive traffic is throttled with clear `429` responses.

## Tech stack

Node.js, Fastify · Laravel, Sanctum, Spatie Permission · Redis · MySQL · OAuth2 · JWT · TOTP
